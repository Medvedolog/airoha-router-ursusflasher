# Два пункта, которые требуют решения по объёму

Оба вынесены из патча намеренно: это не однострочные правки, и у каждого
есть развилка, которую выбирать вам.

---

## A. Resume для F5 — дамп и заливка

### Почему это болит

Полный NAND — 256 МиБ. На F5 он идёт кусками по 8 МиБ (`CHUNK_LIMIT`), то есть
32 передачи TFTP, каждая с `mtd read` и `hash sha256` на устройстве. Обрыв на
любом куске сегодня означает начало с нуля:

```python
# backup(), finally:
partial.unlink(missing_ok=True)
```

При этом **в проекте resume уже реализован и работает** — в BootROM-пути
`_capture_bootrom_chunks()` (`proven_backend.py:9405`). Там на каждый кусок
лежит пара файлов:

```text
bootrom-allflash-NN.bin.gz     сам кусок
bootrom-allflash-NN.raw.sha256 sidecar с хешем сырых байт
```

и при повторном запуске кусок не перекачивается, если его хеш совпал с
**текущим** содержимым NAND (`dd | sha256sum` на живом устройстве). Это
важная деталь: доверяют не файлу на диске, а совпадению файла с железом.

### Что предлагаю

Перенести ровно эту механику в `ursus_ws_nand`, а не изобретать свою.

**Дамп.** Писать куски в каталог `<output>.parts/` как `NN.bin` + `NN.sha256`,
собирать итоговый файл только после последнего куска. При повторном входе
пропускать кусок, если `session.sha(...)` после `mtd read` совпал с sidecar.
Это дешёвая проверка: `mtd read` всё равно нужен, а `hash sha256` уже
вызывается.

**Заливка.** Здесь resume опаснее и требует отдельной осторожности. Записанный
блок можно проверить чтением (`mtd read` + `hash sha256`), и если он уже
совпадает с источником — пропустить. Но:

- порядок «загрузочная область последней» обязан сохраниться и при возобновлении;
- пропуск блока допустим только при совпадении **полного** eraseblock;
- карта плохих блоков должна совпадать и с архивом, и с состоянием на момент
  прерывания — иначе возобновление запрещено, нужен полный проход.

### Развилка для вас

1. **Только дамп.** Меньше риска, закрывает самый частый сценарий (снять 256 МиБ
   по капризной сети). ~80 строк.
2. **Дамп и заливка.** Закрывает и обрыв посреди записи, но заливка — путь, где
   ошибка стоит устройства, и resume там добавляет состояние, которого сейчас
   нет. ~200 строк плюс отдельные тесты на порядок блоков и на отказ при
   изменившейся карте.

Моя рекомендация — **вариант 1 сейчас**, вариант 2 после первого аппаратного
прогона F5, когда станет видно, где реально рвётся.

### Чего resume не решает

Пункт 4 исходного разбора — отсутствие отметки прогресса **на устройстве**.
Resume живёт на ПК. Если питание пропало посреди заливки, на самом аппарате
по-прежнему ничто не говорит, докуда дошли; помогает только то, что
загрузочная область пишется последней. Полноценная отметка потребовала бы
энергонезависимого носителя вне переписываемой области — это отдельная задача
с собственным аппаратным приёмочным тестом, и в текущей архитектуре F5 её
места нет.

## B. Терминал по UART

### Почему это почти бесплатно

`ursus_ws_terminal.py` уже написан как транспортно-независимый. Его docstring
говорит это прямо:

> Only the transport differs from the UART terminal: keyboard input and device
> output remain byte streams.

`LiveTerminal.__init__(self, ws, host)` использует от `ws` ровно два метода —
`recv_message()` и отправку. `WebSocketSerial` в `ursus_ws_xmodem.py` уже даёт
интерфейс `read/write/reset_input`, которого хватает `proven_backend.xmodem_send`.
А `RecoverySerial` (`proven_backend.py:6918`) даёт тот же самый интерфейс для
UART.

То есть нужен тонкий адаптер, а не второй терминал.

### Что это даёт

Сейчас вся работа по UART — сценарные мастера: `uart_bootarea_restore.py`,
`perform_stock_restore_in_uboot()`, `bootrom_backup_wizard()`. Интерактивного
приглашения нет. С адаптером появляются:

- те же F2/F3/F4/F5 на аппарате, **у которого Ethernet ещё не поднялся**;
- F5-дамп через UART-управление — но данные всё равно по TFTP, см. ниже;
- единый терминал вместо двух кодовых путей, когда понадобится следующая
  горячая клавиша.

### Где ограничение никуда не денется

F5 по UART **не даёт дампить без сети**. `receive_ram()` построен на `tftpput`,
то есть на Ethernet. В U-Boot нет XMODEM-отправки: `loadx`/`loady` только
принимают. Вычитать по самому UART можно лишь скрейпингом `md`, и для 256 МиБ
это не путь.

Поэтому честный результат адаптера: **управление по UART, данные по Ethernet**.
Полезно, когда WebFailsafe не поднялся, а линк есть. Бесполезно, когда нет
линка вообще.

Если нужен дамп совсем без сети — это другая задача: XMODEM-отправка в самом
UrsusBoot (команда вида `sendx <addr> <size>`), то есть правка прошивки, а не
хоста. Скажите, если это интересно — прикину объём отдельно.

### Развилка для вас

1. **Адаптер `SerialLink` + пункт меню «Живая консоль по UART»** — F2/F3/F4
   работают, F5 работает при наличии линка и честно отказывается без него.
   ~120 строк плюс тест с псевдотерминалом.
2. **То же плюс `sendx` в UrsusBoot** — полноценный дамп без Ethernet.
   Требует сборки прошивки, своего места в бюджете BL33 (после диеты t73 запас
   есть: MD ~60 КиБ, MF ~68 КиБ) и отдельного аппаратного прогона.

Моя рекомендация — **вариант 1**, и отдельно обсудить `sendx`, если сценарий
«нет линка вообще» для вас реален.
